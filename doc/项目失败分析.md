# M576 1310 自校准 — 项目失败分析

> **状态**：截至 2026-07-23，产线仍未稳定跑通「全路径定标 + IL 达标 + 可重复出货」。  
> **定位**：本文是**失败归因**，不是功能说明书。算法细节见 [`算法总览.md`](算法总览.md)、[`经验教训总结.md`](经验教训总结.md)；工程不变量见 `M576Calibrator/Docs/INVARIANTS.md`。  
> **一句话**：在固件扫频/定基能力不足的前提下，要求上位机「无论固件吐什么数据都能准确定标」，把本应是**闭环控制系统**的问题，误当成了**曲线分类 + 补丁堆叠**问题——这在信息论与工程可验证性上都不成立。

---

## 0. 结论先说

| 维度 | 判定 |
|------|------|
| 业务目标 | **未达成**：约三个月（约 2026-04 → 2026-07）反复定标，仍不能稳定全量成功 |
| 表面归因 | 「固件拉胯」——扫频、定 base、判峰能力弱，上位机被迫背锅 |
| 深层归因 | **成功标准被设成不可交付**：上位机须「囊括所有生产情形」；该目标没有有界输入模型、没有可证伪的验收面 |
| 方法失败 | 以 **comm 日志驱动打补丁** 替代 **接口契约 + 物理可观测量验收**；每修一类曲线，产线再出一类新形状 |
| 工程结果 | 工具链（读 BIN / 写 BIN / 烧录 / 日志 / 回归）基本成型；**定标算法主战场陷入补丁循环**，甚至倒逼出 FineTune「人工拧 DAC」兜底 |

**不是「再改两周门限就能成」；是问题定义本身与分工边界错了。**

## 1. 项目想解决什么，实际卡在哪

### 1.1 名义流程（PRD 四步）

1. **Read Bin** — 透传读 2×MCS + 2×1×64 backup  
2. **Calibrate** — Run Path / RECAL 定标（~576 路径 × 多 slot）  
3. **Write Bin** — 合并 1310 低温槽进 backup  
4. **Burn Flash** — 透传烧录  

读/写/烧、透传、归档、IL 挂机弹框等**外围能力已多轮落地**。失败集中在第 2 步：**从固件返回的一维功率序列里，稳定算出正确的 (X,Y) DAC**。

### 1.2 真实卡点（不是「不会发命令」）

- 每步不是真 2D 格点搜索，而是 **Y 预扫 → 锁 Y → X 扫 → 软件交叉**；Y 错则整步系统偏峰。  
- 初值依赖 Flash LUT（`base=9999`），1550/装配偏差大时峰常在窗外。  
- 「寻峰成功」≠「IL 合格」：弱峰、旁瓣、错误 Y 锁死仍可写出 LUT。  
- 产线成功标准是 **端到端 IL / 重复性**，算法中间态却按 **曲线形状门限** 判成败——两套标准长期对不齐。

这句话本身已经点破：**无边界的「全部情形」无法在有限迭代内交付。**

## 3. 为什么「上位机囊括一切」这么难（除了固件差）

### 3.1 信息不足：上位机看到的不是「真峰」，是噪声投影

固件每次只给一条 **有限窗、有限步长、带无效占位** 的 1D 功率序列。上位机要推断的是 MEMS 二维响应面的峰位。

在下列任一条件下，**曲线形态与真峰位置没有唯一对应**：

- 真峰在窗外（只见单调贴边 / 平坦）  
- 窗内是肩、平台、双峰、尖刺噪声  
- PM 挡位错 → 有效点被压扁或打到噪声底  
- 路由/插损异常 → span 极低仍可「拟合出一个峰」  

要求「不管固件发什么都能准确定标」，等价于要求：在**观测不完备**时仍唯一还原物理峰。这不是调参问题，是**不可观问题**。

### 3.2 目标函数错位：产线要 IL，算法在优化「过门限」

| 产线真正关心 | 算法长期在优化 |
|--------------|----------------|
| 端到端 IL、重复性 | Strict/Relaxed、MinProminence、stitch 早停、validate_code |
| 每一步可出货 | 每一步日志里 `peak_ok` |

历史事故（2026-07-08）已证明：**mesa bypass「Succeeded」却写出离谱 DAC、IL 爆表**。  
FineTune 的出现，说明团队已事实承认：**自动寻峰成功 ≠ 可用定标结果**。

### 3.3 「囊括所有情况」没有验收面 → 只能永远补丁

可交付的需求应长这样：

- 输入模型：无效码、噪声、平坦、单调、窗外峰、PM 超档……**有限枚举 + 概率**  
- 输出契约：成功 / 可重试 / 硬失败；失败必须停或人工介入  
- 验收：全路径 IL 分布、FATAL 率、comm 回放回归集  

实际被接受的口头目标是：

> 固件随便吐数据，上位机都要定准。

这把「失败」从系统里抹掉了。于是每次产线挂了，只能：

1. 抓一条新 comm  
2. 加一个分支 / 门限 / phase  
3. CrossPeakTest 过旧用例  
4. 实机再出新形状 → 回到 1  

这是 **过拟合产线日志**，不是收敛的控制系统设计。

### 3.4 补丁互相打架：修边界会伤主流

产线大量路径其实 **首轮 @64 就能过**。为少数坏通道加：

- 扩窗、拼接、Relaxed、mesa、对称三段豁免、fineRefine 回退 stitch……  

会引入：

- 错误成功（写坏 LUT，比 skip 更致命）  
- 扫频次数硬顶、耗时、超时  
- INV 文档与代码双轨不同步，下一次改门限再踩坑  

07-08 mesa 事故、stitch 发 `9799`（把 `9999` 当坐标）等，都是 **策略层自我伤害**，不只是固件。

### 3.5 验证闭环太慢，迭代效率被物理时间锁死

- 一次完整 Run Path：小时级  
- 失败 step 稀疏分布在数百路径 × 多 slot  
- 离线 `CrossPeakTest` 只能回归**已采集形状**；采不到的形状永远测不到  
- 固件/`9999`/col0 语义偏差，理想几何单测**测不出来**  

因此「打了好几遍补丁还不行」是结构性的：每个补丁的真实反馈周期以天计，而坏例空间随设备/装配/波长漂移在变。

### 3.6 分工错位：把固件能力缺口当成上位机 KPI

项目规则写得很清楚：上位机在补固件不足。但产线压力把这句话扭曲成：

> 固件可以继续弱，上位机必须兜住一切。

合理分工应是：

| 层 | 应保证 |
|----|--------|
| 固件 | 扫频窗语义清晰；无效点稳定；能按显式 base 扫；最好能粗定峰或上报可信 col0 |
| 上位机 | 在**契约内**做重试、拼接、验收、拒绝写坏 LUT |
| 工艺/光路 | 初值不要离谱到窗外不可恢复；连接与挡位可控 |

当契约不存在时，上位机只能无限扩张策略树——**这就是三个月算法主战场打不穿的根因**。

## 4. 已投入的补丁类型（为何仍不够）

下列均为「已做大量工作」仍未闭环的证据，而非能力不足的借口：

1. **启发式 recenter**（Flat / 单调贴边 / 扩 offset / 平移 base，多 attempt）  
2. **粗扫 + 精扫**（64 / 200 / fineRefine）  
3. **拼接式 Pipeline**（stitch k0..k4、merge、早停、PM explore 特殊处理）  
4. **平台峰 / dual_knee**（已引入又因 IL 事故移除）  
5. **PM 挡位与 `opm` 防卫**（INV-16/17）  
6. **Y 交叉失败回炉**（INV-19）  
7. **门限统一**（去掉多套 flat 语义并存）  
8. **comm 回放 + CrossPeakTest + FA 脚本**  
9. **FineTune 人工槽道补写**（承认自动路径兜不住）  

模式固定：**每一种补丁解决一类日志指纹，同时制造下一类边界。**  
在「必须囊括未知的全部情形」压力下，这棵策略树没有停止条件。

## 5. 失败类型拆分（避免再笼统说「算法不行」）

| 类型 | 表现 | 靠上位机堆策略能否根治 |
|------|------|------------------------|
| A. 通信/协议/超时 | 串口、透传、应答缺失 | 否 → 工程加固即可，不是主矛盾 |
| B. 观测窗外真峰 | 平坦/单调/stitch 打满 | **否** → 需更好初值或固件扩搜/粗峰 |
| C. 窗内多解/弱峰 | peak_ok 但 IL 差 | **否** → 需 IL/功率验收，禁止盲写 LUT |
| D. 策略自伤 | mesa 直成功、错误 DAC 公式 | 是 → 已部分修，但证明「过拟合补丁」风险极高 |
| E. 工艺/光路 | 特定 slot/step 高发 | 否 → 难通道清单 + 硬件/装配，不是再加 if |

当前失败叙事常把 B+C+E 全部甩给「再优化 PeakFinder」。  
**B/C/E 占比不降，算法再改也不会「突然全绿」。**

## 6. 组织与需求层面的失败（技术之外）

1. **成功标准不可证伪**：「囊括所有情况」无法写进 DoD，也无法在评审里说「够了」。  
2. **固件与上位机没有冻结接口**：`9999`、col0、无效功率、扫频点数等靠实机反推，文档滞后。  
3. **用产线事故驱动设计**：07-08 一类事故会逼出大改；大改后缺少「IL 门禁禁止烧录」的硬闸，坏结果仍可能落盘。  
4. **工具化很强、问题定义很弱**：Harness、INV、CrossPeakTest、归档都做了；但核心问题一直是「没有有界的定标契约」。  
5. **沉没成本**：拼接/mesa/多轮优化投入越大，越难承认「该停在契约边界并打回固件/工艺」，于是继续补丁。

## 7. 若重新定义成功，什么才算「可交付」

下列任一不做，就不应再承诺「全自动准确定标」：

1. **冻结固件扫频契约**（命令、col0、无效码、显式 base、超时、最大窗）并版本化。  
2. **验收前移到 IL/功率**：`peak_ok` 只是中间态；超差禁止 Write/Burn。  
3. **承认有界失败**：打满 pipeline → FATAL / 人工 FineTune / 返修，而不是再加第 N 种形状检测。  
4. **初值策略产品化**：backup LUT / 邻道 / 难通道表作首轮 base，而不是无限依赖 `9999`。  
5. **固件补能力或减负**：粗峰、可信窗、或模块级把 1550 初值拉到可搜范围——否则整机上位机永远在不可观区间猜峰。

在上述契约建立之前，继续堆寻峰补丁，**预期仍是：局部 comm 变绿、全局产线仍红。**

## 10. 结语

这个项目难搞，核心不是「再缺一个绝妙拟合公式」，而是：

**在观测不完备、契约未冻结、成功标准无界的条件下，用无限补丁去逼近「无论固件发什么都能准」——这是一个不可能在有限工期内收敛的目标。**

三个月证明了：外围工程可以做成；**在错误的成功定义下，定标算法主战场成不了。**  
下一步若仍只加 PeakFinder 分支而不重定分工与验收，重复失败的概率极高。



###还值得做的

高 ROI（证明边界，而不是再堆启发式）：

IL Test：无光 / 功率过低即判定 Invalid，不计 Span——否则验证在给算法泼脏水。
定标后：写 bin → 烧录 → 立即回读对照，出「槽位一致性」报告。
对坏通道做 「写入 DAC vs 人工最佳 DAC」 偏差统计——这才是算法对错的硬尺子。
把 FATAL / PmRange / 通信超时 / 无效功率占比做成一页 dashboard，给评审看失败 taxonomy。
